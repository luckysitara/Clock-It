Verdict: NOT ready for mainnet. The program has a live collateral-theft vector, permanently frozen funds on every native-SOL exit path, and a release-profile arithmetic-wrap exploit. The mobile app's money layer is largely simulation: the default borrow/repay/P2P/staking flows write Memo instructions (or fail account validation) while the UI reports success and credits balances the chain never verified. 24/24 tests pass, but only InitializePool is exercised through a real runtime — the 13 "security" tests are pure-math unit tests.

1 · Smart Contract — Critical

CRITICALC-1 · Anyone can steal defaulted pool collateral
program/src/processor.rs:1364–1516 (process_claim_default, LoanOrder branch)

The pool-loan liquidation path performs no caller authorization and no destination validation. Any signer can claim a defaulted loan (after grace expiry) and route 100% of the collateral to any account they pass — including their own. The docs claim "Caller (Pool Authority, LP, or P2P Funder)"; the code checks caller == offer.funder only in the P2P branch. For native SOL it even credits the attacker's lamports directly (destination_collateral_account.try_borrow_mut_lamports()).

Scenario: borrower misses a repayment → anyone triggers grace (no auth there either) → 24 h later the first caller routes the collateral to their own wallet. The lender (pool) loses the collateral; the protocol earns nothing.
Fix: require *caller.key == pool.authority, require *destination_collateral_account.key == pool.vault_pda (or a caller-owned account with an owner check), and slash/penalize only after validation.
CRITICALC-2 · Direct lamport debits on non-owned accounts — SOL collateral permanently frozen
program/src/processor.rs:1084–1087, 1218–1221, 1400–1405, 1556–1559, 1702–1704, 1736–1741

The Solana runtime only allows an account's owner program to debit its lamports (InstructionError::ExternalAccountLamportSpend). Escrow accounts here are never owned by ClockLend: native-SOL escrows are created by SystemProgram.transfer (owner = system program), and SPL escrows are token accounts (owner = token program). Every exit path that does **escrow.try_borrow_mut_lamports() = … therefore reverts at runtime:

  • Repay of native-SOL-collateral pool loans — fails → borrower cannot repay, ever.
  • Claim default (native SOL, both loan and P2P) — fails → no liquidation possible.
  • P2P repay / cancel (native SOL) — fails.
  • Cancel P2P offer (SPL, lines 1736–1741 drains token-account rent) — fails → unfunded SPL offers can never be cancelled; collateral locked forever.
Scenario: a user borrows against 0.5 SOL → tries to repay → tx reverts → collateral stuck in escrow for everyone, including the liquidator.
Fix: for native SOL, CPI system_instruction::transfer(escrow, dest, amt) with invoke_signed using the escrow PDA seeds; for SPL, CPI spl_token::instruction::close_account for rent. Never mutate lamports of foreign-owned accounts directly.
CRITICALC-3 · Release arithmetic wraps — P2P collateral seizure exploit
program/Cargo.toml (no [profile.release]) · processor.rs:673, 886, 1298, 1319

Cargo.toml has no [profile.release] overflow-checks = true, so release/SBF builds use wrapping arithmetic. now + duration_seconds can wrap negative. In process_fund_p2p_offer the creator sets duration_seconds (only <= 0 is rejected — no upper bound), so a malicious creator or funder picks a huge duration: due_time wraps into the past → grace can be triggered immediately → funder claims the creator's collateral 24 h later while the creator keeps the principal. In pools, a hostile pool authority can set max_duration similarly and trap borrowers.

Fix: add [profile.release] overflow-checks = true; use checked_add for all clock math; cap duration_seconds (e.g. ≤ 365 days).

2 · Smart Contract — High

HIGHH-1 · Treasury accounts never validated — all fees caller-routable
processor.rs:587–651, 993–1055, 1397–1497 · TREASURY_SEED (state.rs:13) is dead code

The 0.25–0.50% origination fee, the 15% interest take-rate, and the 5% liquidation margin are routed to whatever account the caller passes as "treasury". The only checks are treasury.key != borrower.key-style key comparisons. A borrower passes their own second token account → pays zero fees. A liquidator passes their own account → pockets the margin too. The program has no canonical treasury PDA.

Fix: derive and enforce a canonical treasury PDA ([TREASURY_SEED]), validate it in every fee route, and reject any other account.
HIGHH-2 · SKR "reputation bonding" is theater
processor.rs:332–426 (process_stake_skr)

skr_escrow_account is never validated — not against a PDA, owner, or mint — so a user can pass their own second wallet as "escrow" and keep full control of the tokens. No mint check on user_skr_account: any SPL token (e.g. fake airdrops) can be staked to inflate staked_skr and the "verified merchant" status. There is no UnstakeSKR instruction at all — legitimately staked SKR is locked forever. The "slashable default guarantee" only decrements a counter; it never touches tokens.

Fix: validate escrow = program PDA, validate SKR mint from a program config account, add UnstakeSKR (and only then implement slashing against the escrow).
HIGHH-3 · No oracle — the "strict LTV enforcement" compares raw units 1:1
processor.rs:474–482

max_borrow = collateral_amount × max_ltv_bps / 10000 compares lamports (1e9/SOL) against USDC micro-units (1e6/USDC) with no price feed and no decimal normalization. 1 SOL (≈$150) of lamports "supports" ≈500 USDC at 50% LTV — an effective LTV of ~330%. The README's headline security claim is meaningless as implemented.

Fix: per-mint decimal/price normalization (oracle, or at minimum a program-owned price table with authority-gated updates).

2b · Smart Contract — Medium / Low

  • M-1 Borrow records collateral_mint from the untrusted parameter without cross-checking the escrow token account's actual mint; the escrow token account itself is never validated (owner/authority/mint). A malicious client can record a mint that doesn't match the escrowed asset, breaking repay/liquidation (processor.rs:444, 531–567).
  • M-2 TriggerGracePeriod requires only any signer (docs say "Borrower or Circle Member") — griefing/early-grace spam (processor.rs:1274–1330).
  • M-3 FundP2POffer / repay / grace / claim never check is_initialized; a zeroed PDA deserializes as status = Open and is fundable (processor.rs:848).
  • M-4 Instruction docs for BorrowFromPool don't match the implementation's account order (docs: profile@8; impl: token@8, system@9, profile@10, treasury@11) and the profile account is read but never used (_user_profile_opt) — the "SKR discount" feature is dead code (processor.rs:584).
  • L-1 interest_due as u64 truncation for absurd pool configs (max_duration / interest_rate_bps unbounded at init). Use try_into().
  • L-2 Repay accepts repay_amount > total_due; overpayments inflate total_liquidity accounting beyond the vault balance (withdraw self-DoS later).
  • L-3 #[allow(deprecated)] system_instruction module used (works, but the deprecated API should be migrated).

3 · Mobile App — Critical

CRITICALMC-1 · Borrow, repay, fund, and stake never touch the real program
src/solana/onChainService.ts:790–850, 890–930, 999–1041 · App.tsx:380–455, 486–501

isPoolLiquid is always false (no pool has liquidity — DepositLiquidity is never built), so buildBorrowTx takes the "Devnet Protocol Liquidity Mode" branch: a SystemProgram.transfer of 100% of the user's SOL collateral to an escrow PDA derived from a random, never-created loanId, plus a Memo. Nothing can ever spend those lamports (no LoanOrder PDA exists for RepayLoan; cancel requires a program-owned offer account). The UI then credits the borrowed USDC, shows "Loan Disbursed on Solana!" and "Received $X USDC" — the USDC is fabricated.

buildRepayTx with isPoolLiquid=false emits only a Memo; the app deletes the order, returns the displayed collateral, boosts reputation and asserts "Successfully repaid … collateral unlocked from escrow." On-chain, the loan is still Active, interest accrues, and the collateral is liquidated at grace expiry. Same pattern for P2P funding (memo only) and P2P repayment (memo only) — while buildCreateP2POfferTx transfers real SOL to an escrow whose offer PDA was never created, and cancel can never succeed.

Fix: delete the memo branches entirely. Build the real instructions (BorrowFromPool, RepayLoan, FundP2POffer, CreateP2POffer), require a funded pool (or fail loudly), and only update local state after the program account confirms the new state.
CRITICALMC-2 · LoanOrder parser shifted 32 bytes — garbage shown to users
src/solana/onChainService.ts:224–264

The Rust LoanOrder is 154 bytes including a pool pubkey at offset 41 that the parser skips. Every field after offset 41 is read 32 bytes too early: principalAmount becomes the first 8 bytes of the pool pubkey (≈1e13 "USDC" displayed as "Total to Repay"), and status is read from an interest byte — so loans whose interest LSB happens to equal 2 are silently hidden from the Active Orders list, and others are mislabeled.

Fix: correct offsets — principal@73, mint@81, collateral@113, interest@121, origination@129, due@137, grace@145, status@153.
CRITICALMC-3 · Math.random() CSPRNG fallback
src/polyfill.ts:35–64

If native getRandomValues throws, the polyfill silently falls back to Math.random() (Hermes xorshift128+ — predictable from a few outputs) for tweetnacl.randomBytes, Keypair.generate(), and every web3.js RPC id. Today no keypairs are generated (MWA signs), which is the only thing keeping this from being an immediate key-compromise; the moment a seed/dApp-keypair flow is added it becomes catastrophic.

Fix: never fall back — use expo-crypto and throw new Error('CSPRNG unavailable').

6 · What's done right

  • Key hygiene (mobile): no seed/mnemonic/key material anywhere in src/ (grep-verified), no AsyncStorage, nothing sensitive logged; all signing goes through MWA/Seed Vault with proper APP_IDENTITY and a reauthorize fallback.
  • PDA seed derivations match the program exactly (all 7 seeds, u64 LE encoding, bump handling), and the P2POffer/LendingPool parsers match the Rust layouts byte-for-byte.
  • Lamport math is done properly where it's done: Math.round(x*1e6) + explicit writeU64LE — no float truncation.
  • Program foundations: consistent PDA validation via find_program_address, owner checks on state accounts, token/system program ID checks, checked math in most accounting paths, checks-effects-interactions ordering, and a solid create_or_allocate_pda front-run-injection defense.
  • P2P claim default is properly authorized (funder-only + destination owner check) — the pattern the pool-loan path should copy.
  • Defensive mobile patterns: try/catch on every RPC/sign path, cancellation mapped to friendly copy, chain-first/cache-fallback data loading, SNS lookup timeouts, Promise.allSettled parallel loads, devnet-only guard for mainnet.

7 · Recommended fix order

  1. C-1 + C-2 + C-3 (program): authorization, lamport CPIs, overflow checks — the three live exploits/fund-freezes.
  2. H-1 (program): canonical treasury PDA + validated fee routing.
  3. MC-1 (mobile): delete memo paths; wire real instructions end-to-end; chain-verified state only.
  4. MC-2 + H-2 (mobile): fix LoanOrder offsets, UserProfile length, StakeSKR account order.
  5. H-2 (program): SKR mint validation + UnstakeSKR.
  6. H-3 (program): per-mint price/decimal normalization for LTV.
  7. Mobile: CSPRNG fallback, lock-screen hardening, Preview Mode removal, deep-link encoding, double-tap guards.
  8. ProgramTest integration coverage for borrow/repay/claim/cancel/stake/grace.
