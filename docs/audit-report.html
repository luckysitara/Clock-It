Headline

The program survived the merge intact: all six round-7 fixes are present, 83/83 tests pass, and the hand-rolled PriceUpdateV2 parser was validated byte-exact against a live mainnet account. The hardening in 67d2ad7 is real (Full-only verification, +60s future-skew bound).

Critical findings

CRITICAL C-1

Pyth ephemeral signer is never signed — borrow & create-offer fail 100% whenever Hermes is reachable

mobile/src/solana/onChainService.ts:971-975 · seekerWallet.ts:256-258

tx.partialSign(...att.signers) runs on a new Transaction() with no recentBlockhash → web3.js throws Transaction recentBlockhash required before signing. The unshift happened first, so the phantom postUpdateAtomic instruction stays in the tx; the catch swallows the error; the instruction declares the ephemeral price-update keypair as a required signer nobody ever signs → tx rejected at signature verification. Even if it had signed, signAndSendSeekerTransaction overwrites recentBlockhash/feePayer after signing, invalidating the signature anyway.

Today this is inert only because Hermes v2 returns 401 without an API key, so the attach throws before the unshift. The moment an API key is added, every borrow and pawn creation breaks — the exact inverse of the intended fail-open design.

Fix: set blockhash/feePayer before attaching signers; make signAndSendSeekerTransaction only fill them if unset (never overwrite a signed blockhash); move the unshift after a successful partialSign.
✔ VERIFIED — code path reproduced; web3.js throw behavior confirmed; overwrite confirmed at seekerWallet.ts:256-258
CRITICAL C-2

Full-only gate vs the atomic Pyth path: works today by a 1-signature margin, dead tomorrow

mobile/src/solana/pyth.ts:28,148 · program/src/pyth.rs:154-167

The deployed GuardianSet under the Wormhole bridge (HDwc…) has 5 keys → quorum 4 (verified on-chain: account 8d9szT…, index 1). The client trims Hermes VAAs to 5 signatures, so today a post can reach VerificationLevel::Full — by exactly one signature. If Pyth rotates the set to 8+ keys (quorum 6), every client post becomes Partial and every borrow/create-offer reverts with InsufficientVerificationLevel — total liveness failure with no on-chain signal. Independently, Hermes v2 now rejects keyless requests (HTTP 401 verified live), so the client path is dead in practice today, and SKR collateral has no canonical fallback — SKR loans depend entirely on the dormant keeper's admin feed staying inside its 3600s staleness window.

Either (a) accept Partial{n} only when n ≥ quorum(current on-chain guardian set), or (b) keep Full-only and have the client check the VAA's signature count against the on-chain set before attaching (fall back to the canonical account otherwise), or (c) drop atomic posting and pin canonical sponsored accounts for both SOL and SKR. Add an integration test generated the way the client generates its VAA.
✔ VERIFIED — GuardianSet on-chain (5 keys, quorum 4); Hermes 401 reproduced; program gate confirmed Full-only; SKR fallback absence confirmed
CRITICAL C-3

Program-id keypair missing — first mainnet deploy cannot sign

mobile/scripts/deploy-mainnet.mjs:74

The script deploys with bare --program-id HAjGxuih…. On a cluster where the program account does not exist (mainnet — verified: not found), the CLI rejects with “Initial deployments require a keypair be provided for the program id”. The keypair for HAjGxuih… is on no keyring and in no file on this box: id.json → BEmX…, deployer → 5avuk…, keeper → HtiDpTk…, and target/deploy/clock_lend-keypair.json was silently regenerated to 517Dh4d… by the last build. Devnet still upgrades (account exists); mainnet cannot bootstrap until the original keypair is recovered from backup — or a new program id is chosen end-to-end.

Recover the keypair and pass the file (--program-id /path/HAjGxuih….json); add a preflight comparing solana-keygen pubkey $PROGRAM_KEYPAIR to PROGRAM_ID. If lost: pick a new id and update lib.rs declare_id!, program.ts, runbook, seed scripts.
✔ VERIFIED — all four keypairs on disk checked; CLI first-deploy behavior reproduced on a local validator
CRITICAL C-4

--create-pool sends a 62-byte InitializePool; borsh requires 63

mobile/scripts/deploy-mainnet.mjs:159-162 · program/src/instruction.rs:15-28

InitializePool carries a trailing is_oracle_free: bool (added in F7), so borsh requires 63 bytes. The script builds 62 (tag + pool_id + pool_type + 2×u16 + 2×i64 + name[32]). Verified against the real program on a local validator: 62 bytes → InvalidInstructionData; +1 zero byte → decodes to business logic. The runbook's one-command bootstrap dies at the last step, after program/admin/feeds are live. seed_devnet.mjs and seed_pool2.mjs share the 62-byte payload and additionally omit the token-program account → also dead.

Append Buffer.from([0]) /* is_oracle_free */ (plus a --oracle-free flag); fix or delete the two seed scripts; add an ops smoke test that runs the script end-to-end on devnet.
✔ VERIFIED — payload bytes counted; behavior reproduced on local validator against the real program
