2 · Program — CRITICAL (new)

CRITICALC-1 · Type confusion: LoanOrder ⇄ P2POffer aliasing breaks the entire P2P lifecycle
state.rs:182,287 (both LEN == 162, no discriminator) · processor.rs:1769/2117/2240 (LoanOrder tried first)

Every 162-byte P2POffer deserializes as a valid LoanOrder (status byte comes from grace_period_expires[0] = 0 → Active; is_active = is_initialized = 1). Repay / grace / claim all dispatch into the LoanOrder branch and return there, so the P2P branches are dead code:

  • RepayLoan on a funded offer: loan.pool = offer's funder (an on-curve wallet); the check "a program-owned account with key == loan.pool" can never pass → creator can never repay. PoC-verified: Custom(0) InvalidInstruction with the exact amount.
  • ClaimDefault by the funder: fails in the loan branch (no such pool) → funder can never liquidate. PoC-verified: Custom(19).
  • TriggerGracePeriod by the creator "succeeds" before the real due date (parsed loan.due_time = offer's created_at, always past) and writes with LoanOrder offsets into the offer → corrupts state; offer status stays Funded.
Every funded P2P pawn is a one-way transfer: the creator keeps the principal forever, the funder has zero recourse, and the collateral is frozen in escrow for both parties.
Fix: give every account struct an explicit 8-byte discriminator (or an AccountKind tag) and require it at every entry point; never dispatch on parse success. Make the two types different sizes as defense-in-depth.
CRITICALC-2 · CreateP2POffer re-initializes a FUNDED offer — creator keeps principal AND collateral
processor.rs:1573–1579

The re-init guard rejects only status == Open. A Funded (or Repaid/Defaulted) offer passes, and the creator (who controls offer_id, and thus the PDA) overwrites the live loan record back to Open, funder = default. They then call CancelP2POffer and reclaim the escrow. PoC-verified end-to-end: create → fund (funder's USDC moves) → re-create same offer_id → cancel → creator receives the entire escrow. Repeatable per funder.

Fix: require!(!existing.is_initialized) — forbid PDA reuse outright (or require a terminal state + program-version tag).
CRITICALC-3 · InitializeAdmin is first-caller-wins — LIVE ON DEVNET
processor.rs:729–771 · devnet admin PDA 9vX4JBN5h4YhEDKFwFQgki6czmgkLPUz8hLs2iwZn7Hq is currently uninitialized

No check ties the caller to the deployer/upgrade authority; whoever calls first becomes permanent admin (no rotation instruction exists). The admin is the only party who can create global price feeds, and price_micro_usd has no upper bound (only ≠ 0). An attacker who claims admin sets SOL at u64::MAX micro-USD and — because the borrow scan accepts the global feed even when a pool-scoped feed exists — drains every USDC vault against dust collateral.

This is raceable right now on devnet, and again after every redeploy: front-run the deployer's InitializeAdmin transaction (it is a separate tx from the BPF upgrade).
Fix: derive the admin from the program's upgrade authority (bpf_loader_upgradeable::get_program_data_address) or hardcode the deploy key; bound price_micro_usd and decimals. Immediately: call InitializeAdmin yourself on devnet.

3 · Program — HIGH

  • H-1 · FundP2POffer hijacks live loans. It performs no PDA derivation — only an owner check. A 162-byte LoanOrder parses as an Open P2POffer (status byte = locked_skr high byte = 0), so an attacker "funds" a victim's loan with junk tokens: loan.pool is overwritten with the attacker's off-curve wallet key, making the loan permanently unrepayable and unliquidatable — collateral frozen, total_borrowed desynced forever, borrower escapes penalties. PoC-verified (probe B, two auditors).
  • H-2 · Protocol revenue is permanently burned. Fees route to the [b"treasury"] PDA, but no instruction can spend from it (no WithdrawTreasury; the PDA is off-curve). All origination fees, 15% of interest, and 5% liquidation margins are destroyed. On devnet the treasury has no token accounts at all (verified), so every fee-bearing borrow, repay, or liquidation currently fails outright.
  • H-3 · Borrower chooses the price feed. The borrow scan accepts the global feed even when the pool has provisioned its own pool-scoped feed — no precedence rule. No pool can enforce conservative pricing; combined with C-3 it is a protocol-wide drain.
  • H-4 · CreateP2POffer's LTV gate is decorative. The optional oracle account is positional with no PDA, mint, authority, or staleness validation (1527–1547) — a creator passes any program-owned PriceFeed (e.g. one they initialized as their own pool authority) to list worthless collateral at 150% LTV.
  • H-5 · Pool params unvalidated at init (regression). No bounds on interest_rate_bps, max_ltv_bps, min_duration, max_duration. A hostile pool sets min_duration = -1: borrower passes duration = -1 → duration as u128 = 2⁶⁴−1 → ~5.8e7× interest on a 1-unit loan, and due_time in the past → instant grace + liquidation in 24h.
  • H-6 · Feed decimals unvalidated; 10^decimals can panic. decimals comes from the keeper unchecked; decimals ≥ 39 panics 10u128.pow() (probe-verified), and decimals = 0 for a 6-decimal mint inflates collateral value 10⁶×.
  • H-7 · DepositLiquidity = gift to the pool authority. No LP shares/claims exist; authority-only WithdrawLiquidity can pull any deposit immediately. Third-party "liquidity providers" have no claim at all (README markets pro-rata yield).
