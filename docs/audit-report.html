Critical findings

CRITICAL C-1

Share inflation: cached total_staked_skr + unstake that never decrements = one stake drains the dividend pool

program/src/processor.rs:3582-3588 (claim sync) · 725-815 (unstake) · 3596-3607 (no-profile branch)

vault.total_staked_skr is only ever mutated inside process_claim_skr_yield, from profile.staked_skr + locked_skr. process_unstake_skr returns the SKR to the user and never touches the yield vault, and the claim path's no-profile branch keeps earning on the cached position.staked_skr. Exploit: stake X → ClaimSkrYield (registers X shares) → UnstakeSKR (SKR back, shares remain) → repeat with N fresh accounts re-staking the same X → N·X shares against X real escrowed SKR. On the next dividend the attacker's positions claim ~all of it (payout is first-come, capped by the vault token balance); honest stakers receive 0 and their accrued_rewards is silently written off. Cost to the attacker: transaction fees only.

Derive stake from the real SKR escrow token account balance (spl_token::state::Account::unpack(&skr_escrow...)) instead of the cached counter — or at minimum decrement vault.total_staked_skr in process_unstake_skr (and the ClaimDefault slash path) and make the profile account mandatory on the claim path.
✔ VERIFIED — claim sync reads the profile counter; unstake grep-shows zero yield-vault references; no-profile branch re-earns cached stake
CRITICAL C-2

InitializeSkrYieldVault is permissionless AND has no is_initialized guard — anyone can zero the vault and strand all rewards

program/src/processor.rs:3355-3399

create_or_allocate_pda returns Ok when the account is already program-owned, and there is no is_initialized read anywhere in the handler — so a second call unconditionally packs a fresh zeroed vault: acc_reward_per_share = 0, total_staked_skr = 0, pending_rewards = 0, authority = caller. The PDA is derived from reward_mint only, so any wallet can call it. Consequences: every user's stored reward_debt now exceeds staked·acc/1e12 → all accrued rewards compute to 0 (stranded), and with total_staked_skr == 0 all subsequent deposits stop updating acc → permanently unclaimable dividends. This is repeatable sabotage, and it also lets anyone race the team for first-call ownership of the vault (the authority field is currently read nowhere, but any future consumer inherits the hole).

Unpack first and bail: if existing.is_initialized { return Err(...) }, and gate first init on the AdminConfig admin (same pattern as WithdrawTreasury).
✔ VERIFIED — no is_initialized check; zeroed struct packed unconditionally; no admin/authority check in the handler
CRITICAL C-3

Deploy script ships a stale artifact — today's deploy would silently omit round-8 hardening AND the yield feature

mobile/scripts/deploy-mainnet.mjs:106-109 · program/target/deploy/clock_lend.so

The script's only check is fs.existsSync(soPath) — it never builds and never compares freshness. The artifact on disk (300,104 bytes, md5 189a61df, mtime 2026-09-23 09:30) predates both the round-8 commit (09:46) and the yield sources — all five program/src/*.rs files are newer. Running the runbook command today write-buffers and upgrades that old ELF, prints "MAINNET BOOTSTRAP COMPLETE", and ships a program without the Pyth Full-verification hardening, the ±staleness bounds, the allowlists, or the yield feature.

Preflight: run cargo build-sbf (or hard-fail without --skip-build); fail if any program/src/** file or program/Cargo.lock is newer than the .so; print md5 + size before upload.
✔ VERIFIED — mtimes and md5 checked; all five source files newer than the artifact

High findings

HIGH H-1

The yield feature is inert in the shipped client — and the deployed program can't run it anyway

mobile/src/solana/onChainService.ts:1954 · program/src/instruction.rs:210-240

buildClaimSkrYieldTx has zero callers; there are no buildInitializeSkrYieldVaultTx / buildDepositSkrYieldTx builders at all; no UI screen wires it; and buildBorrowTx never appends the two yield-vault PDAs, so the program's 50/50 origination-fee split never fires from the app — the vault can never be funded in production. The deployed program (devnet) predates tags 15–17, so a claim would revert with invalid-instruction-data even if wired. ✔ VERIFIED — grep: zero callers

Either ship it (add the two missing builders, append the vault PDAs in buildBorrowTx gated on vault-is-initialized, add UI gated on an on-chain CLK_SYLD read) or cut the dead code until the upgrade lands. Don't ship a live-looking claim path against an un-upgraded program.
HIGH H-2

No time weighting / cooldown — JIT front-running snipes origination-fee dividends

program/src/processor.rs:3467-3475, 3644

Accrual is purely by acc_reward_per_share snapshot; last_interaction_time is recorded but never enforced. Both deposit triggers (permissionless DepositSkrYield and the borrow-path fee split) are observable before they land, so an attacker can stake in slot N, register shares, let the dividend land in N+1, claim pro-rata, and unstake in N+2 — capital returned, zero holding risk, disproportionate payout. ✔ VERIFIED in source — no time check on the claim path

Time-weighted accrual (per-slot reward_rate with last_acc_update), or a minimum stake age before claimability.
HIGH H-3

DepositSkrYield is permissionless and the reward mint is unrestricted at init

program/src/processor.rs:3417, 3342

Only assert_signer — no vault-authority/treasury/admin check, so anyone can push rewards at any time and thereby control exactly when acc moves (who gets entitled), or interleave dust deposits to shift rounding. Init accepts any reward_mint pubkey. ✔ VERIFIED in source

Gate deposits on vault.authority (with a rotation path proving upgrade authority), allowlist reward_mint to {USDC devnet/mainnet, SKR}. If the drip is meant to be permissionless, add epoch pacing so it can't control accrual timing.
HIGH H-4

SOL collateral sizing always uses a hardcoded $150.0 — the live-price lookup can never match

mobile/src/components/P2PExpressView.tsx:43

solHolding = tokenList.find(symbol === 'SOL') is always undefined — tokenList comes from getParsedTokenAccountsByOwner, which never contains native SOL — so 150.0 is always used. That flows into the on-chain collateral amount: the tx reverts InvalidCollateralRatio when the price is above market and silently over-locks when below. Two hardcoded SOL prices coexist (150.0 here, 101.12 in livePrices). ✔ VERIFIED

Use livePrices.sol (already fetched every 120s); disable the borrow CTA with "price unavailable" when stale rather than substituting a constant.

HIGH H-7

Dividends deposited while total_staked_skr == 0 are permanently stranded

program/src/processor.rs:3467 (deposit), 1588 (borrow split)

Both allocation sites skip acc_reward_per_share when total_staked_skr == 0 but still credit pending_rewards — and claims pay only staked · acc / 1e12, which never includes that money. The first dividend (e.g. keeper deposits before any user syncs) is lost forever. On devnet this is 100% of routed revenue, because the SKR mint doesn't exist there. ✔ VERIFIED in source

Add an unallocated_rewards field rolled into the next acc increase, or reject deposits while total_staked_skr == 0.

  • M-1 No solvency invariant between pending_rewards and the vault token balance — over-claimers silently write off other users' accrued rewards (only payout = claimable.min(vault_tok.amount) stands in the way).

  • M-3 P2PExpressView banners fabricate "protocol fee dividends" on escrowed collateral and "Liquid Staking APY" — escrowed SKR earns nothing; no LST exists in the program (allowlist rejects those mints; only a stale comment mentions JitoSOL/Sanctum).
  • M-4 Free-text collateral parsing: "2 JitoSOL" silently escrows 1.0 native SOL; bare "SKR" escrows 1000 SKR; SOL detection inconsistent across three code paths.
  • M-5 Order-cache network namespacing half-applied — App.tsx:343/427/513 still call setCachedOrders without the network arg (cross-network loan leakage when the toggle is used).
  • M-6 Claim builder assumes the reward ATA exists — intermittent InvalidAccountData exactly when there is something to claim.
  • M-7 NoYieldToClaim error is never returned (dead code); runbook has NO yield section; test count stale (88 vs 96); BorrowFromPool doc comment omits the two new optional accounts.
  • M-8 InitializeSkrYieldVault unauthenticated (folded into C-2; the authority field it records is currently unread — a trap for future handlers).
