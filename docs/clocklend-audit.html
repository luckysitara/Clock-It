ClockLend Security Audit

The program cannot originate a loan, cannot repay one, and cannot liquidate one. Five critical findings, four of them proven by executing the attack against the program in a local SVM.

Verdict

Do not deploy. The loan lifecycle is unreachable end to end. Three independent blockers sit in series: no instruction can create the token accounts the protocol depends on (F-02), borrowing is gated behind a profile account the client cannot have (F-07), and repayment reverts on a Rust borrow error before any token moves (F-01).

Separately, the economic layer has no price input and no mint allowlist (F-03), and every protocol fee is opt-in by the borrower (F-04) — so even once the blockers are cleared, any pool holding real value can be drained at the cost of an SPL mint.

Scope and method

Two surfaces were reviewed: the native Rust Solana program in program/src (~2,500 lines) and the React Native / Android client in mobile/src. The bundled Tardis/ directory was excluded by request.

Findings were derived by reading source, then the critical paths were executed against the real program using solana_program_test. Where a PoC runs, the report says so and includes the code. Where a claim rests on reading alone, it is marked Static — those have not been run and should be verified before being treated as settled.

Executed Partial Static

A note on the test suite. The README advertises “24/24 Tests Passing · Security Audit Status”. The suite is 31 tests, and the 19 in security_tests.rs never invoke the program — each re-implements the arithmetic in the test body and asserts on local variables. test_security_claim_default_pool_authority_enforced asserts that two freshly generated random public keys differ. Passing tests are not evidence of a working program here, and this report does not treat them as such.

03

Blocker 1 — the lifecycle cannot complete

F-01 Critical Executed Repay, grace-period and default revert on a borrow error before any token moves
Where program/src/processor.rs — 8 sites Impact Repayment, grace period, liquidation all dead

A temporary created in an if let scrutinee lives until the end of the if let block in Rust 2021 — this crate's edition. So the immutable Ref handed back by try_borrow_data() is still held when the block body asks for a mutable borrow of the same account:

processor.rs — the reproducerrust
// processor.rs:1141 — the borrow below is live for the WHOLE block
if let Ok(mut loan) = LoanOrder::unpack_from_slice(&loan_account.try_borrow_data()?) {
    ...
    // processor.rs:1184 — mutable borrow of an already-borrowed account
    loan.pack_into_slice(&mut loan_account.try_borrow_mut_data()?)?;
    //                                                        ^ runtime error:
    // "instruction tries to borrow reference for an account which is already borrowed"
}

The borrow path uses the same idiom but writes after the block closes, which is why it works — and why the bug stayed hidden. That is the second line of the reproducer below.

PoC-5 · minimal reproducerrustc --edition 2021
use std::cell::{Ref, RefCell, RefMut};
struct Acct { data: RefCell<Vec<u8>> }
impl Acct {
    fn try_borrow_data(&self) -> Result<Ref<'_, Vec<u8>>, String> {
        self.data.try_borrow().map_err(|_| "AccountBorrowFailed".to_string())
    }
    fn try_borrow_mut_data(&self) -> Result<RefMut<'_, Vec<u8>>, String> {
        self.data.try_borrow_mut().map_err(|_| "AccountBorrowFailed".to_string())
    }
}
fn unpack_from_slice(src: &[u8]) -> Result<usize, String> { Ok(src.len()) }

fn main() -> Result<(), String> {
    // processor.rs:1141 — borrow inline in the if-let scrutinee, write inside
    let a = Acct { data: RefCell::new(vec![0u8; 154]) };
    if let Ok(_loan) = unpack_from_slice(&a.try_borrow_data()?) {
        match a.try_borrow_mut_data() {
            Ok(_)  => println!("REPAY  if-let scrutinee -> no conflict"),
            Err(e) => println!("REPAY  if-let scrutinee -> {e}"),
        }
    }

    // processor.rs:671 — same borrow, but the write happens AFTER the block
    let b = Acct { data: RefCell::new(vec![0u8; 154]) };
    if let Ok(_e) = unpack_from_slice(&b.try_borrow_data()?) {
        println!("BORROW inside if-let (read only)");
    }
    match b.try_borrow_mut_data() {
        Ok(_)  => println!("BORROW after if-let     -> no conflict"),
        Err(e) => println!("BORROW after if-let     -> {e}"),
    }
    Ok(())
}

// Output:
//   REPAY  if-let scrutinee -> AccountBorrowFailed
//   BORROW inside if-let (read only)
//   BORROW after if-let     -> no conflict

Confirmed against the live program: a real RepayLoan transaction returns TransactionError(InstructionError(0, AccountBorrowFailed)).

Impact Loans can never be repaid, so collateral can never be returned. Grace periods can never be triggered, so defaults can never be marked or liquidated — escrowed collateral becomes permanently unreachable.

Fix. Bind the borrow to a let before the if let — the pattern process_cancel_p2p_offer already uses correctly at :1988:

processor.rs — corrected shaperust
let mut loan = {
    let data = loan_account.try_borrow_data()?;
    LoanOrder::unpack_from_slice(&data)?
};                       // Ref dropped here

loan.status = LoanStatus::Repaid;
loan.pack_into_slice(&mut loan_account.try_borrow_mut_data()?)?;   // no conflict

Evidence gap. RepayLoan is proven by execution. TriggerGracePeriod and ClaimDefault share the identical code shape across 6 further sites but were not executed — reaching due_time requires the clock to advance, and ProgramTest's clock does not advance per transaction. Treat them as near-certain and re-verify after the fix.

Blocker 2 — the accounts cannot exist

F-02 Critical Executed No instruction creates the vault, escrow or treasury token accounts
Where program/src/processor.rs — vault :264, escrow :648, SKR escrow :405, treasury :750 Impact Deposits, borrows and staking all fail

Four PDAs must be SPL token accounts, but all four are Program Derived Addresses — off-curve, with no keypair. Only the owning program can create an account at such an address, by signing with invoke_signed and the PDA seeds. ClockLend never does:

terminalverification
$ grep -rn "initialize_account\|create_associated\|InitializeAccount\|associated_token" program/src/
$ echo $?
1        # zero matches — the program never creates a token account

The 12-variant instruction enum has no vault, escrow or treasury initializer. Consequence: DepositLiquidity transfers into a non-existent account and fails, so a pool can never hold liquidity and BorrowFromPool can never succeed. StakeSKR and UnstakeSKR fail the same way.

This was confirmed by executing the only client-side route to creating such an account — create_account, which requires the new account to sign:

PoC-1 · vault PDA cannot be created by a clientrust

Impact The protocol is non-functional before any economic logic is reached. The devnet program ID in lib.rs:7 and the README cannot have working deposit, borrow or stake flows.

Blocker 3 — collateral is never valued

F-03 Critical Executed Self-minted tokens stand in for real collateral and borrow real liquidity
Where processor.rs:614-630 Impact Any funded pool can be drained Cost to attacker One SPL mint

The collateral ratio is computed with no price feed and no mint allowlist. collateral_mint is attacker-supplied and only inspected to decide whether it is native SOL; nothing binds it to a real asset:

processor.rs:614-630rust
let collateral_value = if is_native_sol && !is_pool_native_sol {
    // SOL collateral (9dp) vs USDC pool (6dp), base rate $150/SOL  <-- hardcoded
    (collateral_amount as u128 * 150_000_000u128) / 1_000_000_000u128
} else if !is_native_sol && is_pool_native_sol {
    (collateral_amount as u128 * 1_000_000_000u128) / 150_000_000u128
} else {
    collateral_amount as u128        // <-- raw units, no valuation at all
};

let max_borrow_allowed = collateral_value
    .checked_mul(pool.max_ltv_bps as u128).ok_or(ClockLendError::AmountOverflow)?
    / 10000u128;
if (borrow_amount as u128) > max_borrow_allowed {
    return Err(ClockLendError::InvalidCollateralRatio.into());
}

When the collateral and the pool's declared liquidity mint sit on the same side of the native/SPL split, the else branch is taken and one raw token unit counts as one raw unit of the borrowed asset. An attacker who controls a mint supplies that collateral.

Fix. Replace the branch with a real price source and an explicit mint allowlist carrying per-asset decimals and price; reject any collateral mint not on it. A hardcoded price is not an oracle.

Critical — economics

F-04 Critical Executed Every protocol fee is skipped when the caller omits an optional account
Where borrow :752-822 · repay :1202-1288 · default :1680 Impact Protocol has never collected revenue

Fees are applied only inside if let Some(treasury_account) = treasury_account_opt. That slot is filled by scanning whatever extra accounts the caller chose to append — so the borrower decides whether to pay:

processor.rs:742-822 — fee is caller-optionalrust
while let Ok(acc) = next_account_info(account_info_iter) {
    if acc.owner == program_id && acc.data_len() == UserProfile::LEN {
        user_profile_opt = Some(acc);
    } else {
        treasury_account_opt = Some(acc);      // caller-controlled
    }
}

if let Some(treasury_account) = treasury_account_opt {
    // ... net_disbursement to borrower + origination_fee to treasury
} else {
    // NO FEE: full borrow_amount straight to the borrower
    invoke_signed(&spl_token::instruction::transfer(
        token_program.key, vault_account.key, borrower_liquidity_account.key,
        vault_account.key, &[], borrow_amount), ...)?;
}

PoC-2 exercised this: the borrower received 650.000000 USDC rather than 646.750000 after a 0.50% origination fee, and the vault fell by exactly 650.000000. The mobile client never appends a treasury account (onChainService.ts:797-809 and :862-873), so the 15% interest take-rate and the 5% liquidation margin are dead in practice too.

Impact All protocol revenue — origination fee, interest take-rate, liquidation margin — is opt-in by the party who pays it. The economic model described in the README has never run.

Fix. Make the treasury a required account and derive the canonical treasury PDA unconditionally, instead of treating its absence as “no fee”.

A transfer that cannot cover the amount owed returns Ok with a partial payment. In ClaimDefault the lender can be “paid” less than the collateral recorded against the loan while the loan still flips to Defaulted, leaving no on-chain signal that the obligation was not met. This is the same silent-clamp pattern that lets the accounting drift in F-10 go unnoticed.

Impact Silent partial settlement; accounting errors become invisible rather than reverting.
F-09 High Static Loan accounts are drained but never closed, and rent is not restored on reuse
Where :1350-1359, :1472-1481, :63-109

The “close” on repayment drains every lamport on the account to the borrower and zeroes the data, but never reallocates to zero or reassigns to the system program:

processor.rs:1350-1358rust

    **borrower.try_borrow_mut_lamports()? = borrower.lamports().checked_add(rent_lamports)?;
    **loan_account.try_borrow_mut_lamports()? = 0;
    loan_account.try_borrow_mut_data()?.fill(0);  // data zeroed; account still allocated

The PDA survives as a zero-lamport, non-rent-exempt program-owned account. Separately, create_or_allocate_pda returns Ok without restoring rent when the account is already owned by the program (:106-109), so a re-borrow that reuses the same loan_id writes into an unfunded account. The same shape appears in the P2P path at :1472-1481 and :2073-2079.

Impact Non-standard account lifecycle; predictable reuse of an account left in an invalid rent state. Verify against a live validator before relying on either path.

F-11 Medium Static The declared liquidity_mint is never bound to the vault's real mint
Where :609-611 vs :343-358, :764-840

initialize_pool stores liquidity_mint and never checks it again. is_pool_native_sol — which selects the decimals used for valuation — is derived from that stored value, while every actual transfer uses the vault's real mint. The two can disagree, so the LTV math can be applied with the wrong decimal assumption. DepositLiquidity likewise never verifies that the depositor's token account matches the pool's declared mint.

Impact Mispriced collateral whenever the declared and actual mints differ in decimals.
F-12 Medium Static A defaulted loan record can be overwritten by re-borrowing the same ID
Where :1671-1673 and :670-676

ClaimDefault sets is_active = false without zeroing the account, and the reuse guard in borrow only rejects an account whose is_active is true. A borrower can therefore re-borrow using the same loan_id and overwrite the Defaulted record. The reputation penalty already applied is not reversed, but the on-chain history is erased.

Impact Loss of default history on an account meant to be the protocol's credit record.

What is sound

Most of the above is bad news, so it is worth recording what held up under review — and one hypothesis that did not.

  • No leaked secrets. No private keys, mnemonics or API keys anywhere in mobile/. Signing is delegated to the Mobile Wallet Adapter; there is no local key material, no Keypair, no fromSecretKey.
  • The deep link is not a signing vector. clocklend:// is exported and browsable, but App.tsx:154-181 only sets a tab and raises a toast. No signature, no fund movement.
  • Hardening that is claimed is implemented. FLAG_SECURE, the anti-emulator, anti-root and anti-Frida checks all exist and are wired into MainActivity.kt.
  • Liquidation authorisation is correct. ClaimDefault restricts the caller to the pool authority (:1620) or the P2P funder (:1820), and validates destination ownership.
  • Arithmetic hygiene is good. checked_add/checked_mul throughout, overflow-checks = true in both profiles, PDAs re-derived with find_program_address before use, and correct checks-effects-interactions ordering in the paths that do reach their transfers.

A hypothesis that failed. On inspection, **acct.try_borrow_mut_lamports()? = acct.lamports()… (:138, :1352) looked like a RefCell deadlock — the same account on both sides of an assignment. It is not. Rust evaluates the right-hand side before the left-hand place, so the immutable borrow is released first. This was verified by execution and is not a bug; it is recorded here so the pattern is not “fixed” on a false premise.

10

Remediation sequence

The order matters: F-01 sits in front of almost every other test. Until loan state can be written, no repayment, liquidation or accounting check can be exercised at all.

  1. Fix the if let borrow pattern — F-01

    Bind each try_borrow_data() to a let before the if let, at all 8 sites. Without this, no other finding can be verified end to end.

  2. Add the missing account initialisers — F-02, M-02

    Add an InitializeVault / InitializeEscrow / InitializeTreasury instruction using invoke_signed with the PDA seeds, and update the client to call them. Settle this design with the client together — they are missing the same instruction.

  3. Replace collateral valuation with a real price source — F-03, F-11

    A mint allowlist carrying per-asset decimals and a switchable oracle. Delete the hardcoded $150. Verify the declared liquidity_mint against the vault on every deposit.

  4. Make fee and treasury accounts mandatory — F-04, F-10

    Derive the canonical treasury PDA unconditionally rather than inferring “no fee” from absence, and credit total_liquidity with what the vault actually received.

  5. Validate the SKR mint and make slashing real — F-05, F-06

    Pin the SKR mint as a constant and check it on stake. Either move slashed tokens to the lender or remove the bond concept — leaving them stranded is the worst of both.

  6. Fix the client's interest math and signing config — M-01, M-03, M-04

    Read the rate and duration from on-chain state, compute in integers, and match the program exactly. Correct the devnet mint constants and give release builds a real keystore before anything ships.

  7. Rebuild the test suite around real invocations

    Every finding above survived a green 31-test suite. Replace the arithmetic-restating tests with ProgramTest flows: initialize → deposit → borrow → grace → default, plus the negative cases (fake collateral, absent treasury, missing profile). A suite that cannot fail is not evidence.

11

Limits of this audit

  • Sandbox, not a validator. All PoCs ran against solana_program_test's in-process SVM. Behaviour around rent exemption and account lifecycle (F-09) in particular should be re-checked against a live validator before being relied on.
  • Injected fixtures. For F-03, F-04 and F-05 the vault, escrow and treasury accounts were injected with add_account — something a real client provably cannot do, as PoC-1 shows. Those tests validate the logic downstream of bootstrapping; they are not an end-to-end exploit against a deployed program. The conclusions hold because the missing valuation and the optional-fee design are independent of how the accounts came to exist.
  • Two claims unexecuted. TriggerGracePeriod and ClaimDefault share F-01's code shape but were not run — ProgramTest's clock does not advance per transaction, so due_time is unreachable mid-test.
  • Unverified mobile findings. M-07 and the deep-link, ProGuard and manifest claims came from a survey pass and were not independently confirmed. Everything else attributed to mobile/ was read directly.
  • Not reviewed: Tardis/ (excluded by request), dependency versions, and the build pipeline beyond the Android signing configuration.
